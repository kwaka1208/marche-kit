# 設計思想と3層モデル

## 解こうとしている問題

イベントの公式サイトで一番手間がかかるのは、作ることではなく**開催直前の更新**です。

出店者が30店あれば、紹介文と商品情報が30通り集まります。締切を過ぎてから届く原稿、
直前の商品変更、当日の完売報告。これを運営が一手に引き受けると、担当者の作業量が
そのままボトルネックになり、サイトの情報は実態から遅れていきます。

marche-kit は**出店者自身に更新権限を渡す**ことでこれを解きます。
運営の確認は挟まず、保存した瞬間に本番へ反映されます。
運営には通知だけが飛び、間違いがあれば後から直せばよい、という運用です。

### なぜ承認フローを入れないのか

入れた瞬間に、運営が再びボトルネックになるからです。
出店者は自分の店の情報について当事者であり、間違える動機がありません。
実運用で問題が起きていないため、この設計を維持しています。

## 3層モデル

マルシェの物理構造をそのまま設計の語彙にしています。

```
        ┌─────────────────────────────────┐
        │  Auvent — 日よけの布(テーマ)      │  ← 掛け替える
        │  CSS / レイアウト / 配色 / フォント │
        ├─────────────────────────────────┤
        │  Halle — 市場の屋根(コア)         │  ← 共通
        │  PHP / 描画JS / エディタ          │
        ├─────────────────────────────────┤
        │  Étal — 各店の陳列台(データ)      │  ← イベントごと
        │  shop-data / news / shops         │
        └─────────────────────────────────┘
```

### Halle（コア）— `core/`

仕組みの本体です。すべてのイベントで共通で、原則として編集しません。

- **PHP** — 出店者情報の受信と保存、お知らせJSONの書き込み、メール送信
- **描画JS** — JSONを読んでDOMを組み立てる。カード、ポップアップ、フィルタ、シャッフル
- **文言辞書** — 画面に出す文字列（日本語・英語を同梱）
- **エディタ** — 出店者用と運営用の2種類の編集画面

Halle が守る約束は一つだけです。**決められたクラス名とDOM構造を出力する。見た目は決めない。**

### Auvent（テーマ）— `themes/`

見た目のすべてです。イベントごとに自由に作り替えます。

- CSS変数（配色、余白、角丸、影、フォント）
- レイアウト（セクションの並び、グリッドの列数）
- 装飾（背景画像、区切り線、アニメーション）

Auvent が守る約束も一つです。**Halle が出力するクラス名にスタイルを当てる。DOM構造を前提にしたJSは書かない。**

### スロット — HalleとAuventの接点

この2つがどこで出会うかというと、**スロット**です。
ドキュメント全体で使う言葉なので、ここで決めておきます。

> **スロット**とは、テーマがHTMLに置く**空の要素**のことです。
> コアはそれを探し、見つけたものの中身を作ります。

テーマが書くのは、この1行だけです。

```html
<div data-marche-shops="stalls"></div>
```

コアがこれを見つけて、`shops.json` と各店のデータから出店者カードを組み立てます。
**空の `<div>` が、読み込み後にはカードの並んだグリッドになります。**

| | 決めるもの |
|---|---|
| テーマ | スロットを**どこに置くか**、どう囲むか、CSSでどう見せるか |
| コア | スロットの**中に何を作るか**（カード・リンク・入力欄） |

スロットには2通りあります。

- **中身をコアが作るもの** — 空で置く（出店者カード、商品、お知らせ、SNS、フォーム）
- **コアが値を流し込むもの** — テーマが構造ごと書き、コアは文字や画像だけ入れる（ポップアップ）

**スロットが無ければ、コアは何もしません。エラーも出しません。**
これは「**要らない機能はスロットごと消せる**」ということです。
夜市テーマは、メニューの開閉ボタンのスロットを置いていません（下部固定ナビには不要なため）。

一覧は[テーマ仕様](theme-contract.md)にあります。

### Étal（データ）— 運用データ

イベントの中身です。出店者エディタから書き込まれ、Gitでは管理しません。

- `marche.config.json` — イベント設定（開催日・対価の表示方法・文言の言語）
- `shops.json` — カテゴリ定義と、どの店が出店するかの一覧
- `shop-data/<店舗ID>/data.json` + 画像 — 各店の実データ
- `news.json` — お知らせ

## 動作の前提

| 項目 | 内容 |
|---|---|
| サーバー | セキュリティサポートが継続しているPHPが動く一般的なレンタルサーバー（[対象](setup.md#動作要件)） |
| データベース | 使わない。すべてJSONファイル |
| ビルド | **要らない。** ESモジュールとPHPをそのまま置いて動かす |
| 実行時通信 | 出店者・お知らせ・商品グリッドは**ブラウザからJSONをfetch**して描画 |

### なぜグリッドを静的化しないのか

出店者の表示順を**毎回シャッフルする**ためです。
どの店が最初に表示されるかは集客に影響するので、公平性のためにランダム化しています。
ビルド時に順序を固定すると、この公平性が失われます。

代償として、出店者情報は検索エンジンとJS無効環境から見えません。
**これは承認済みのトレードオフです。**
検証時は URL に `?fixed` を付けるとシャッフルが止まり、データ順で固定表示されます。

### なぜお知らせを静的化しないのか

再ビルドとデプロイなしに更新するためです。
イベント直前や当日は、運営がターミナルを開ける状況にあるとは限りません。

古い情報を見せないことを優先し、ブラウザ側のキャッシュ（stale-while-revalidate）は
**意図的に採用していません**。取得に失敗したときは、成功したふりをせずエラーを表示します。
