# 設計上の決定

naracraft.beer の実装を marche-kit として一般化するにあたり、決めたことの記録です。
各項目は「現状 → 何が困るか → **決定** → 検討したが採らなかった案」の順です。

決定日: 2026-08-30 / 対象: 段階1（実装着手前）

## この文書の位置づけ

段階1で、本家の実装に埋め込まれた特定イベント向けの前提を7つの論点として洗い出し、
それぞれに選択肢を添えて提示しました。この文書はその**回答を受けて確定させた結果**です。
論点集そのものは役目を終えたため、この決定記録に統合しています。

各決定に「**検討したが採らなかった案**」を併記しています。
一度検討して却下した案を再提案しないための記録です。
前提が変わって再検討するときは、まず却下理由がまだ有効かを確かめてください。

## 1. 出店者カテゴリは設定で定義する

### 現状（naracraft.beer）

`shops.json` のキーが `breweries` と `foodstores` の2つに固定され、
描画先のDOM IDも `#breweries-grid` / `#foodstores-grid` で決め打ちでした。

### 何が困るか

マルシェなら「野菜・加工品・雑貨・キッチンカー」、朝市なら「鮮魚・青果」のように、
区分の数も名前もイベントごとに違います。2種類固定では最初の1歩で詰まります。

### 決定

ロスターをカテゴリの配列に変え、区分そのものをデータで定義します。

```json
{
  "categories": [
    { "id": "breweries",  "label": "ブルワリー", "variant": "feature", "shops": ["choryo-brewery"] },
    { "id": "foodstores", "label": "フード",     "shops": ["yamato-tacos"] }
  ]
}
```

**旧形式（`breweries` / `foodstores` をキーにする形）は読みません。** 切り捨てます。

描画先は固定IDをやめ、テーマ側がスロットに属性で指定します。
カテゴリを増やすとき**テーマのHTMLに1行足すだけ**で済みます。

```html
<div class="shop-grid" data-marche-shops="breweries"></div>
```

### カテゴリごとに見た目を変える

**data属性と variant の併用**にします。コアはカードに両方を出力します。

```html
<div class="shop-card-info shop-card--feature" data-category="breweries">
```

| 手段 | 用途 | テーマの使い回し |
|---|---|---|
| `shop-card--<variant>` | **こちらを主に使う。** 見た目のバリエーション | ○ 他イベントでも当たる |
| `[data-category="..."]` | このイベント専用の微調整 | ✗ カテゴリ名が変わると当たらない |

`variant` の語彙は `standard`（既定）/ `compact` / `feature` の3つです。省略時は `standard`。

テーマは **`variant` だけを見て書くのが基本**です。カテゴリIDに直接スタイルを当てると、
そのテーマは他のイベントで使えなくなります。逃げ道として残しますが、常用しません。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| 旧形式（カテゴリ名をキーにする形）の読み込み互換を残す | 2形式の分岐がコアに残り続ける。移行が必要なのは本家1サイトだけなので、切り捨てるほうが安い |
| `data-category` のみ（variant なし） | テーマがイベント固有のカテゴリIDを知ることになり、他イベントに持っていくとCSSが1つも当たらない |
| `variant` のみ（data-category なし） | 「このカテゴリだけロゴを大きく」のような例外的な微調整ができない。逃げ道がないと結局コアを直すことになる |
| カテゴリごとにHTMLテンプレートを差し替える | 最も柔軟だが、コアがテンプレートエンジンを持つことになる。「コアは見た目を決めない」原則と衝突し、仕様が「クラス名」から「テンプレートの書き方」に膨らむ |

## 2. 開催日は設定で定義する

### 現状

商品の販売日が `both` / `dayA` / `dayB` の3値で、**2日間開催が前提**でした。
表示ラベル（「3日(土)のみ」など）は描画JSとエディタに直書きでした。

### 何が困るか

1日開催、3日開催のイベントで破綻します。日付の表記も毎年書き換えが必要でした。

### 決定

開催日をサイト設定に配列で持ちます。IDは **`day1` / `day2` / … の連番**とし、
後ろの数字だけが変わる形にします。

```json
"days": [
  { "id": "day1", "date": "2026-10-03", "label": "10月3日(土)", "shortLabel": "3日(土)" },
  { "id": "day2", "date": "2026-10-04", "label": "10月4日(日)", "shortLabel": "4日(日)" }
]
```

商品側は**日のIDの配列**を持ちます。省略時は全日です。

```json
"saleDays": ["day1"]
```

ラベルは設定から取るので、年度更新はサイト設定の1箇所で完結します。
旧形式（`both` / `dayA` / `dayB`）は読みません。

**1日開催のとき（`days` が1件）は、販売日のUIを出しません。**
サイト表示からもエディタの選択欄からも消えます。「初日のみ」の選択肢に意味がないためです。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| 旧形式（`both` / `dayA` / `dayB`）を読み替えて互換を保つ | 2日開催の前提がコードに残り続ける。移行は変換スクリプト1本で済む |
| 日のIDを `dayA` / `dayB` のまま英字連番にする | 3日目以降が `dayC` となり、設定の `days[2]` との対応が直感的でない。数字なら添字と揃う |

## 3. 語彙を改名する

### 現状

コード全体で `menu`（商品）、`brewery` / `foodstore`（出店者）という語が使われ、
CSSクラス名にも `menu-card-top` / `menu-image` として現れていました。

### 何が困るか

雑貨のマルシェで `menu` は不自然です。第三者がコードを読むとき、
`menu` がナビゲーションメニューなのか商品なのかも紛らわしくなります。

### 決定

| 旧 | 新 |
|---|---|
| `brewery` / `foodstore` / `vendor` | **`shop`** |
| `menu` / `menus` | **`item`** / `items` |

クラス名も追随します（`menu-card-top` → `item-card-top` など）。

**この改名は段階3の着手前に完了させます。** クラス名はテーマ仕様の一部であり、
後から変えると既存のテーマがすべて壊れるためです。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| 出店者を `vendor` にする | `shops.json` / `shop-data/` と語が揃わない。`shop` に一本化するほうが読み手の負担が少ない |
| 商品を `product` にする | やや長く、体験やサービスを売る出店者にはかえって窮屈 |
| `menu` のまま据え置く | 雑貨のマルシェで不自然。ナビゲーションメニューと紛らわしく、第三者がコードを読むとき詰まる |

## 4. 表示文言を辞書に外出しし、英語辞書を同梱する

### 現状

「完売しました」「読み込み中…」「過去のお知らせを見る」などがコードに直書きでした。

### 決定

文言を辞書JSONにまとめ、サイト設定の `locale` で選びます。
**日本語と英語の辞書を同梱します。**

```
core/i18n/ja.json
core/i18n/en.json
```

本格的な多言語対応（i18nライブラリ、言語切り替えUI、URLの言語別分岐）は入れません。
**辞書1枚で足ります。** サイトごとに一部の文言だけ差し替えられるようにします。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| i18nライブラリを導入する | 依存が増える割に、扱う文言は40件程度。複数形や性数変化も要らない |
| 日本語辞書のみ同梱し、英語は利用者に作らせる | OSS公開の入口として不親切。キー構造の見本にもなるため同梱する |

## 5. チケット運用は price の読み替えで対応する

### 現状

`price` は数値で、表示時に円として整形されていました。

### 何が困るか

イベントによっては、会場共通のチケットを先に買い、商品はチケット◯枚と引き換える
**チケット運用**をとります。この場合に見せたいのは「600円」ではなく「2枚」です。

本家サイトも第6回まではチケット運用で、`tickets` という別フィールドを持っていました。

### 実データから分かったこと

本家の全131商品を調べたところ、`tickets` と `price` の**共存は1件もありませんでした。**

| 状態 | 件数 |
|---|---|
| `tickets` のみ（チケット運用時代） | 75 |
| `price` のみ（金額制移行後） | 44 |
| 両方を持つ | **0** |

運用は排他で、1つのイベントの中で金額とチケットが混在することはありません。

### 決定

`tickets` フィールドは復活させません。`price` を「**対価を表す数値**」と定義し直し、
**表示の単位だけを設定で切り替えます。**

```json
"pricing": {
  "mode": "currency",
  "currency": { "unit": "円", "position": "suffix", "grouping": true, "decimals": 0 },
  "ticket":   { "unit": "枚", "faceValue": 300, "showFaceValue": true },
  "note": "税込"
}
```

**通貨の小数桁に対応します**（`decimals`）。円は `0`、ドルやユーロは `2` を指定します。
チケットモードでは枚数なので、`decimals` は使わず**常に整数**として検証します。

**チケットと現金の併用（「チケット2枚 または 600円」）は対応しません。**
実運用に前例がなく、データ構造が複雑になるためです。

既存の規約はそのまま活きます。`price` が0以下なら未設定とみなして一覧に出さないルールは、
「0枚」が無意味であることと自然に整合します。

### 但し書きも設定から与える

現行実装は商品詳細に「税込」を直書きしていました（`script.js:316`）。
チケット運用では税の概念がないため、これも設定の `pricing.note` から与えます。
**空なら要素ごと出力しません。**

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| `tickets` フィールドを復活させ、`price` と併存させる | 実データで共存が1件もなかった。2つ持つと「どちらが正か」の分岐が全描画箇所に増える |
| チケットと現金の併用を表現する | 実運用に前例がない。データ構造とUIの両方が複雑になり、得るものが釣り合わない |
| 通貨の小数桁を設定に出さない（円は整数なので不要） | 国内前提の判断。OSS公開する以上、ドルやユーロで使えないのは制約が大きい |

## 6. 出店者が入力する文字列はHTMLとして扱わない

### 現状

出店者が編集できる項目のうち、HTMLとして描画される箇所とテキストとして描画される箇所が
混在していました。

| 項目 | 描画方法 |
|---|---|
| 店名（`name`） | 常にHTMLとして挿入 |
| 商品名（`menus[].name`） | 既定は `<br>` を空白に置換してテキスト描画。`allowNameBreaks: true` のときだけHTML |
| 紹介文（`comment`） | `\n` を `<br>` に変換。テキスト扱い |
| お知らせ（`body`） | HTML文字列 |

### 何が困るか

店名と `allowNameBreaks: true` の2経路では、出店者エディタから任意のHTMLを保存できます。
**理屈の上ではスクリプトを仕込めます。**
現行サイトでは出店者が身元の知れた相手であり、実害がないため許容されていました。

しかしOSSとして配布すると、利用者の運用体制はさまざまです。
「出店者を信頼する前提」を暗黙にしたまま配るのは不親切です。

### 決定

**店名と商品名の `<br>` 埋め込みを廃止し、`\n` を改行として扱う方式に統一します。**
`comment` がすでにこの方式で、実績があります。

**`allowNameBreaks` は廃止します。** 統一により不要になります。

**サーバー側でHTMLタグを除去する検証を入れます。**
クライアントを信用せず、保存時にタグを落とします。

**READMEに「出店者を信頼できる範囲で使う仕組み」であることを明記します。**
承認フローを持たない設計である以上、この前提は隠さず書きます。

お知らせの `body` はHTML文字列のままにします。運営しか書けないためです。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| HTMLを許したまま、サニタイズライブラリで無害化する | 依存が増える。**改行のためだけにHTMLを許す必要がそもそもない** |
| `allowNameBreaks` を残し、既定を安全側にしたまま運用する | `\n` に統一すればフラグ自体が不要。設定が1つ減る |
| 出店者を信頼する前提のまま、何も検証しない | 現行サイトでは成立しているが、OSSとして配ると利用者の運用体制はさまざま。前提を暗黙にしたまま配れない |

## 7. 設定をフレームワーク非依存のJSONに集約する

### 現状

サイト共通情報・開催概要・お知らせ設定が、Astroのソース内のTypeScriptファイルにありました。

### 何が困るか

静的サイトジェネレーターを変えると設定ごと移植が必要になります。
またPHP側からは読めないため、設定が二重管理になっていました。

### 決定

イベント設定を `marche.config.json` に集約し、**サイト生成側もPHP側も同じファイルを読みます。**
年度更新がこの1ファイルで完結する状態を目指します。

```json
{
  "site":    { "name": "...", "url": "...", "description": "..." },
  "event":   { "year": 2026, "venue": "...", "hours": "..." },
  "days":    [ { "id": "day1", "date": "2026-10-03", "label": "10月3日(土)", "shortLabel": "3日(土)" } ],
  "pricing": { "mode": "currency", "currency": { "unit": "円", "position": "suffix", "grouping": true, "decimals": 0 } },
  "locale":  "ja",
  "announcements": { "source": "data/news.json", "visibleCount": 3 }
}
```

TypeScriptの型による恩恵は失われますが、二重管理の解消を優先します。
型が必要なら、JSONから型定義を生成する方法をあとで検討します。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| TypeScriptのまま維持する | PHP側から読めず、通知先や開催日の二重管理が続く |
| 設定をPHPファイルに置き、生成側がそれを読む | 静的サイトジェネレーター側からPHPを解釈する必要が生じる。JSONならどちらからも素直に読める |

## 8. 商品カテゴリを設定で定義する

決定日: 2026-08-30 / 段階2

### 現状（naracraft.beer）

商品カテゴリの選択肢が `editor.js` に `beer` / `food` / `other` で直書きでした。

### 何が困るか

決定1で**出店者**のカテゴリは設定に出しましたが、**商品**のカテゴリ（商品一覧の
フィルタに使う別物）には定義場所がありませんでした。エディタが選択肢を出せません。

### 決定

`marche.config.json` に `itemCategories` を持ちます。

```json
"itemCategories": [
  { "id": "beer", "label": "ビール" },
  { "id": "food", "label": "フード" }
]
```

**空または未定義のときは、エディタに商品カテゴリの欄を出しません。**
決定2の「1日開催なら販売日UIを出さない」と同じ流儀です。

受信PHPは、定義があるときだけ `itemCategories[].id` にないIDを拒否します。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| `shops.json` に置く | 出店者のカテゴリと同じファイルになり混同を招く。データ仕様でも「別物」と注記している以上、置き場も分けるほうが読み手に親切 |
| エディタでは自由入力にする | 定義を持たずに済むが、表記ゆれが起きてフィルタが機能しなくなる |

## 9. 販売日はチェックボックスで選ぶ

決定日: 2026-08-30 / 段階2

### 経緯

決定2で `saleDays` を日IDの配列にしました。現行のUIはラジオ3択
（両日 / 初日のみ / 2日目のみ）でしたが、これは2日開催専用の作りです。
3日開催では組み合わせが7通りになり、ラジオでは表現できません。

### 決定

**開催日ごとにチェックボックスを1つ出します。** 配列というデータの形と素直に対応します。
未設定の商品は全日にチェックが入った状態で開きます。

すべての日を選んだ状態と未指定は同じ意味なので、**未指定側に寄せて保存します**
（`saleDays` を書き出さない）。この判断はエディタとサーバーの両方が同じ規則で行います。

**1日も選ばれていないときは送信を止めます。** 空配列を「全日」として黙って保存すると、
出店者の意図（その商品は出さない）と逆になるためです。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| ラジオのまま、選択肢を日数から生成する | 「1日目と3日目だけ」のような組み合わせが表現できない。配列にした意味がなくなる |
| 空配列を「販売日なし」として保存する | 「どの日にも出ない」は販売状態（`status: ended`）で表すべきで、販売日で表すと意味が二重になる |

## 10. 保存はロスターにある店舗IDだけ受け付ける

決定日: 2026-08-30 / 段階2

### 現状

受信PHPは店舗IDのパターン（英小文字・数字・ハイフン）だけを見ており、
ロスターにないIDでもフォルダを作って保存していました。

### 何が困るか

サイトに表示されるのはロスターにある店だけなので実害はありませんが、
直接POSTすれば任意のIDでフォルダを作れます。OSSとして配る以上、
「サーバーは送られてきたデータを信用しない」方針から外れた穴を残したくありません。

### 決定

`shops.json` のいずれかのカテゴリに載っている店舗IDだけを受け付けます。
エディタも同じロスターから店を選ぶので、通常の操作には影響しません。

**`shops.json` が読めないときは検証を省略します。** 設置直後にロスターが
未配置でも詰まらないようにするためです。

## 11. ナビゲーションを固定する位置はテーマが決める

決定日: 2026-08-30 / 段階5

### 現状

ページ内リンクで移動するとき、コアは固定ナビの高さを差し引いて手前で止めていました。
見出しがナビの下に潜り込まないようにするためです。
判定は「`position: fixed` かどうか」だけで、**上にあるか下にあるかを見ていませんでした。**

### 何が困るか

2つ目のテーマ（`themes/night-market/`）でナビを画面の下に固定したところ、
移動先が見出しの高さ分だけ行き過ぎました。下に固定したナビは移動先を隠さないので、
差し引く必要がありません。

マークアップは既定テーマとまったく同じで、位置を決めているのはCSSだけです。
それでも挙動が変わるなら、**「見た目はテーマの自由」という約束が守れていません。**

### 決定

**上端に貼り付いているときだけ高さを差し引きます。**
`getBoundingClientRect().top` が0付近かどうかで判定します（`core/js/ui.js`）。
上に固定したテーマの挙動は変わりません。

`scrolled`（上端から離れたときに付くクラス）は、上に固定したナビのための手がかりです。
下に固定したテーマでは意味がないので、**当てなくて構いません。**

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| 設定やCSS変数でナビの位置を宣言させる | テーマが1つ増えるたびに宣言が増える。**実際の位置を見れば済む** |
| 仕様に「ナビは上部固定を前提」と書いて、コアは変えない | テーマの自由度を、理由の弱い制約で1つ削ることになる |
| `--bottom-nav-height` の値で判定する | 本文の下余白を確保するための変数で、ナビの位置とは別のこと。兼ねさせると意味が濁る |

## 12. イベント公式のSNSはサイト設定に置き、アイコンはテーマが持つ

決定日: 2026-08-30 / 段階6

### 現状

コアはSNSリンクを扱う仕組みを持っていません。出すならテーマのHTMLに
`<a href="https://x.com/…">` を直接書くことになります。
イベント名・会期と同じ扱いで、**テーマがイベント固有の記述を持つ**形です。

### 何が困るか

会期や会場と違い、**SNSのアカウントは運用の途中で増減します。**
「Xだけだったが Instagram も始めた」は、イベントが続くかぎり起きます。
そのたびにテーマのHTMLを直すのは、運営の仕事として重すぎます。

テーマの掛け替えでリンクが消えることも困ります。逆にテーマを他のイベントへ配ると、
**前のイベントのアカウントが付いてきます。** イベントの持ち物がテーマ側にあるのが原因です。

### 決定

`marche.config.json` の `site.social` に配列で置き、コアが `[data-marche-social]` に並べます。

```json
"site": {
  "name": "◯◯マルシェ",
  "url": "https://example.com",
  "social": [
    { "platform": "x",         "url": "https://x.com/example" },
    { "platform": "instagram", "url": "https://www.instagram.com/example/" },
    { "platform": "youtube",   "url": "https://www.youtube.com/@example", "label": "公式チャンネル" }
  ]
}
```

- **プラットフォームは固定しません。** コアが既定の表記を持つのは10種ですが、
  知らないIDでもリンクは出ます（表記は `label` で与える）
- **URLは `http(s)` で始まるものだけ**通します（`shop.url` と同じ規則。決定6）
- 出力は `social-link social-link--<platform>` と `data-platform`。
  カードの `variant` + `data-category` と同じ二段構えです（決定1）
- **アイコンはテーマの持ち物です。** コアが出すのはリンクとクラス名と表記だけで、
  何の絵を出すかはテーマが決めます

対象は**イベント運営のアカウント**です。出店者ごとのSNSは今回入れていません。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| 各社のロゴSVGをコアに同梱する | 見た目がコアに入る。**商標と各社のブランドガイドへの追従を、リポジトリが負い続ける**ことになる。代替画像（`images/noimage/`）がテーマの持ち物であるのと同じ扱いにすれば済む |
| `site.x` / `site.instagram` のようにフィールドを1つずつ生やす | 新しいSNSが出るたびにスキーマとコアを直すことになる。並び順も表現できない |
| プラットフォームの一覧を設定で定義させる（`itemCategories` と同じ形） | 商品カテゴリと違い、**イベントごとに変わるものではない。** 定義を書かせても、どのイベントでもほぼ同じ内容になる |
| 出店者ごとのSNSを同時に入れる | データ仕様・エディタ・PHPの検証・更新通知に波及する。イベント単位のリンクとは検討すべきことが別で、**後から `shop.social` を同じ形で足せる** |

## 13. 問い合わせフォームは astro-courier を移植する（Astroは持ち込まない）

決定日: 2026-08-30 / 段階8

### 現状

`core/php/send.php` はフォームの受信・検証・メール送信を持っていますが、
**画面側がありません**（`core/components/` は未移植のまま）。
定義（`forms/<種別>.json`）とサーバー側の検証はあるのに、入力欄を出すものが無い状態でした。

一方、同じ出自の [astro-courier](https://github.com/kwaka1208/astro-courier) に
そのものの部品があります。Astroコンポーネント `Courier.astro` で、
確認モーダル・ハニーポット・自動再試行・入力保持のエラー復帰を備えています。

### 何が困るか

**そのまま持ち込めません。** `Courier.astro` は Astro のビルドを要求します
（Node 22 / Astro v7）。marche-kit の動作要件は「**ファイルを置けば動く**」で、
これは[意図的にやらないこと](roadmap.md#意図的にやらないこと)の筆頭です。

一方で自前で書き起こすと、上流がすでに解いている問題
（ハニーポットの置き方、CORSプリフライトの回避、送信失敗時に成功を偽らないこと）を
もう一度間違えることになります。

### 決定

**フロントだけを、ビルド不要のESモジュールとして移植します**（`core/js/form.js`）。
バックエンドは既存の `core/php/send.php` のままです。

移植にあたって変えたのは3点だけで、いずれも marche-kit 側の決定に合わせるためです。

| 変えたこと | なぜ |
|---|---|
| 文言をすべて辞書から引く | 決定4。上流は日本語直書き＋`labels` prop。**ブラウザ既定の検証メッセージも使わない**（辞書の言語と食い違うため） |
| 選択肢を `{value, label}` にする | marche-kit の既存スキーマ。上流は `string[]`。送信値と表示を分けられる |
| フロントからのDiscord通知を落とす | サーバー側に `marche_notify_webhook()` がある。**Webhook URLをブラウザに露出させない** |

**クラス名とCSS変数（`courier-*` / `--courier-*`）は移植元のまま残します。**
移植の時点で通っている名前で、**改名しても得るものがないから**です。
marche-kit の命名（`shop-card` など）とは並存します。

**このリポジトリは独立して扱います。** astro-courier を追いかける仕組みは持たず、
移植後の `core/js/form.js` はこのプロジェクトのコードとして手を入れます。
名前を揃えているのは由来を読み取りやすくするためで、同期のためではありません。

壊してはいけない不変条件は上流と同じです。

- `Content-Type` を付けないJSON文字列POST（CORSプリフライトを起こさない）
- ハニーポット・確認モーダル・自動再試行・入力保持のエラー復帰・二重送信抑止
- **送信に失敗したら成功を偽らない**

`marche.config.json` の `forms.endpoint` を空文字にすると、送らずに内容を画面へ出す
モックモードになります（エディタの `UPLOAD_URL` を空にするのと同じ発想）。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| marche-kit に Astro を導入して `Courier.astro` をそのまま使う | 移植の手間は消えるが、**「ファイルを置けば動く」という動作要件を捨てる**ことになる。PHPが動くだけのレンタルサーバーで完結する、という前提そのものが崩れる |
| astro-courier を別に立てて、サイトからリンクする | 実装はほぼゼロだが、見た目とドメインが分かれる。**イベントサイトの中に問い合わせが無い**のは、来場者から見て不便 |
| バックエンドも astro-courier の `php/` に置き換える | 通知先を `config.php` に直書きする作りで、marche-kit の `.env` + `inject-env.py` と食い違う。文言も辞書を使わない。**既存の `send.php` はすでに Courier のペイロードを受けられる**（`submissionId` を除外する処理を持っている） |
| GAS版のバックエンドを選べるようにする | スプレッドシートへの記録（＝確定点）と重複防止が手に入るが、Googleアカウントが要る。**送信先は `forms.endpoint` で差し替えられる**ので、必要になってから足せる |
| 選択肢を上流と同じ `string[]` にする | 既存スキーマを壊す。送信値と表示を分けられなくなり、**ラベルを直すと過去の記録と突き合わせられなくなる** |
| `courier-` を marche-kit 流のクラス名に改名する | 命名は揃うが、**動くものを名前のためだけに書き換える**ことになる。移植元と同じ名前なら、由来も追いやすい |

## 14. イベント名・会期・会場は設定から差し込む

決定日: 2026-08-30 / 段階8のあと

### 現状

`marche.config.json` には `site.name` / `event.venue` / `event.hours` / `days` が揃っています。
しかしコアはそのどれも描画せず、テーマのHTMLに直書きしていました。

```html
<h1 class="site-title">マルシェ</h1>
```

### 何が困るか

READMEとデータ仕様は「**年度更新はこのファイルの修正でほぼ完結します**」と書いています。
実際には**テーマのHTMLも直す必要があり、謳い文句と実態がずれていました。**

会場も開催時間も、運用の途中で変わります。決定12でSNSをスロットにしたのと同じ理由が、
そのまま当てはまります。**テーマを触らずに直せる必要があります。**

### 決定

設定のパスを指定して値を差し込む、汎用のスロットを1つ足します。

```html
<h1 class="site-title" data-marche-text="site.name"></h1>
<span data-marche-text="days.label"></span>
<span data-marche-text="event.venue"></span>
```

**既存の `data-i18n`（辞書を引く）とまったく同じ仕組み**で、引く先が辞書か設定かだけが違います。

- パスはドット区切り。`site.name` / `event.venue` / `event.year`
- **途中が配列なら、その先のキーを各要素から取って連結します。**
  `days.label` → 「10月3日(土)・10月4日(日)」。会期を1つの文字列にするため
- 添字も書けます。`days.0.label` → 「10月3日(土)」
- 値が無いとき、オブジェクトを指したときは**要素を隠します**（`hidden`）
- **隠すときはコンソールに残します。** 綴りを間違えても静かに消えるだけになるため

`<title>` は対象外です。JSで書き換えると読み込み後になり、ちらつきます。
年に一度しか変わらないので、テーマに直書きのままとします。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| 項目ごとに専用スロットを作る（`data-marche-venue` など） | 出したい項目が増えるたびにコアを直すことになる。**設定にあるものは全部出せる**ほうが、コアの変更なしで足りる |
| テーマのHTMLに直書きのまま（現状維持） | 年度更新が設定だけで完結しない。会場変更のたびにテーマを触ることになる |
| `<title>` も差し替える | 描画JSが動いたあとになるためちらつく。年に一度の更新にJSを使う理由が無い |
| 書式（「10月3日(土)〜4日(日)」のような整形）もコアが持つ | 見た目の判断がコアに入る。**連結の区切りは辞書の `common.listSeparator`** に留め、それ以上の整形はテーマのCSSかデータ側で行う |

## 15. デザイントークンの名前は色ではなく役割で付ける

決定日: 2026-08-30 / 段階8のあと

### 現状

配色のトークンが色を名指ししていました。`--white` / `--gray-light` / `--gray-medium` /
`--gray-dark` / `--text-color-dark` / `--text-color-light` /
`--primary-color-dark` / `--primary-color-light` の8つです。

**暗い配色のテーマでは、名前どおりの色が入りません。**

段階5でこの問題に気づいたときは「名前は仕様なので変えられない」として、
値のほうを役割に合わせる形で回避していました。**しかしまだ公開前で、
外部にテーマを配っていません。破壊的な改名のコストが最小なのは今です。**

役割そのままの名前に改名します。**互換のための別名は残しません**

| `--text-color-dark` | `--text-color` | 本文 |
| `--text-color-light` | `--text-color-muted` | 補足文 |
| `--primary-color-dark` | `--primary-color-strong` | 押したとき・ホバー |
| `--primary-color-light` | `--primary-color-subtle` | 淡いアクセント面 |

**値も使い方も変えていません。** 見た目は1ピクセルも変わりません。

`core/editor/editor.css` は改名していません。編集画面はコアの持ち物で、
テーマ仕様のクラス名とも別系統です。**見た目が1つしか無いので、そこでは名前が嘘になりません。**

| 案 | 却下理由 |
|---|---|

## 16. 明暗の切り替えはテーマのCSSで行い、OSの設定に従う

決定日: 2026-08-30 / 段階8のあと

### 現状

暗い配色のテーマは作れます（`themes/night-market/`）が、**1つのテーマが明暗を
切り替える仕組みはありませんでした。** どちらで見せるかは配置時に決まります。

### 何が困るか

閲覧者の端末が暗い設定でも、明るいテーマは明るいまま出ます。
夜のイベントの案内を暗い部屋で見る、という場面は普通に起きます。

### 決定

テーマが `@media (prefers-color-scheme: dark)` で**配色のトークンだけ**を上書きします。
**コアの変更はありません。**

- 上書きするのは配色のみ。余白・角丸・フォントは明暗で変わらない
- **代替画像（`images/noimage/*.svg`）は同じ `@media` をSVGファイルの中に書く。**
  `<img>` で読まれるためページ側のCSSが届かない
- **既定は明るい側に書く。** `@media` が効かない環境ではそちらが出る
- 閲覧者が切り替えるトグルは持たない。OSの設定に従う

`themes/default/` に実装しました。`night-market/` は暗い配色で完結しているため入れていません。

決定15（トークン名を役割で付ける）を先に済ませたので、
`--surface` に暗色を、`--text-color` に明色を入れることに説明が要らなくなりました。
**「強く出る側」を意味する `--primary-color-strong` は、暗い配色では明るい側になります。**

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| 閲覧者が切り替えるトグルを付ける | UIと状態保持（JS・localStorage）が要る。**コアに見た目の判断を持ち込む**ことになり、「コアはクラス名を出力する。見た目は決めない」に触れる |
| コアが `data-theme` 属性を出力し、テーマがそれに当てる | 同上。切り替える主体をコアが持つことになる |
| 代替画像を明暗中立な配色にして、切り替えを諦める | どちらの配色でも中途半端に浮く。段階5で「どこに出るかで明暗を決める必要がある」と確かめた通り |
| 代替画像を2枚用意し、`<picture>` で出し分ける | コアが `<img>` を出力しているため、コアの変更が要る。**SVGの中で解決できるなら、そのほうが小さい** |

## 17. フォントの読み込みはテーマが受け持つ（外部Webフォントも可）

決定日: 2026-08-30 / 段階8のあと

### 現状

同梱の2テーマは `--font-family-main` にシステムフォントを並べているだけで、
`@font-face` も `<link>` もありません。**Webフォントを使いたくなったときの置き場が
決まっていませんでした。**

### 何が困るか

イベントごとに書体を変えたくなったとき、どこに書けばよいか判断できません。
設定（`marche.config.json`）に置く案もあり得ますが、決めていませんでした。

### 決定

**テーマが受け持ちます。** 設定には置きません。

フォントは見た目そのもので、Auvent の領分です。設定に置くと**コアが `<head>` に
`<link>` を挿すことになり、「コアはクラス名を出力する。見た目は決めない」の一線を越えます。**
決定12（SNSを設定に置いた理由）も当てはまりません。**アカウントは運用中に増えますが、
書体は増えません。**

**外部のWebフォント（CDN）も認めます。** 書き方は2通りで、テーマがどちらを選んでもかまいません。

- 外部から読む … `index.html` の `<head>` に `<link>`
- 自前で置く … `tokens.css` に `@font-face`（CSSだけで完結する）

条件は2つだけです。

1. **フォールバックを必ず残す。** 配信元が落ちても文字は読める
2. **`display=swap` を付ける。** 取得中に文字が消えない

### 「レンタルサーバーだけで完結する」との関係

当初、外部CDNは「PHPが動くレンタルサーバーだけで完結する」に反すると考えましたが、
**これは筋が通りません。** その要件は**運営が用意すべきインフラ**の話で、
データベースも管理画面フレームワークも要らない、という意味です。
**閲覧者はすでにインターネット経由でサイトに到達しています。**

フォールバックさえ残せば、フォントは無くても動く見た目の上乗せです。
README の「外部SaaSも使いません」も、この意味では変わりません。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| `marche.config.json` に `site.fonts` を置き、コアが `<link>` を挿す | **コアが `<head>` を触る＝見た目を決める**ことになる。書体は運用中に増えないので、決定12の理由も当てはまらない |
| 外部CDNを禁止し、自前配信のみとする | 「自己完結」を理由にしたが、閲覧者はすでにインターネットを使っている。**禁止する根拠にならない**（IPが渡る点は使う側が判断すればよい） |
| `@import` を推奨する | CSSの取得が終わってからフォントの取得が始まるため遅い |

## 18. 商品情報は「掲載しない」を既定にし、3段階から選ぶ

決定日: 2026-09-02

### 現状

商品はコアの主要な機能でありながら、出すかどうかを設定で決められませんでした。
出るかどうかを決めていたのは**テーマにスロットがあるかどうか**だけです
（`[data-marche-items]` を置けば商品一覧が出て、`.shop-popup-items` を置けば
店舗ポップアップに取り扱いが出る）。

### 何が困るか

第一に、**掲載範囲がテーマの持ち物になっていました。** テーマを掛け替えると、
イベントが商品を出すかどうかまで変わります。「コアはクラス名を出力する。見た目は決めない」
の裏返しで、**テーマが運用方針を決めてしまう**状態です。

第二に、**商品を持たないイベントが素の状態ではありませんでした。**
出店者の紹介だけで完結する催し（展示・体験・相談ブース）でこのキットを使うと、
同梱テーマがそのまま「商品」の見出しと空の一覧を出します。
消すにはテーマのHTMLを削るしかなく、**イベントごとの改造**になります。

第三に、**商品一覧を出すかどうかと、商品の詳細を見せるかどうかは別の判断**です。
「一覧に並べるほど商品数は多くないが、店ごとの取り扱いは見せたい」は自然な運用ですが、
これを表す手段がありませんでした。

### 決定

`marche.config.json` の `items.display` で3段階から選びます。**未定義の既定は `none`。**

```json
"items": { "display": "none" }
```

| 値 | 商品一覧のセクション | 店舗ポップアップの取り扱い | 商品ポップアップ |
|---|---|---|---|
| `none`（**既定**） | 出ない | 出ない | 開かない |
| `popup` | 出ない | 出る | 開く |
| `list` | 出る | 出る | 開く |

- **既定を `none` にします。** 商品を出すのは「そう決めたイベント」で、
  設定に1行書くのはその意思表示です。**逆にすると、商品を持たないイベントが
  「消す作業」から始まる**ことになります
- 綴り違い・未知の値は `none` に落とします（掲載しない側に倒す）
- `none` と `popup` では、**テーマにスロットがあっても埋めません。**
  掲載範囲を決めるのは設定であって、テーマではありません
- セクションを隠すときは、**それを指すナビゲーションの項目も隠します**
  （押しても何も起きないリンクを残さないため）。お知らせ・フォームにも同じ扱いを広げました
- **掲載しない設定でも、登録済みの商品データは消しません。**
  エディタは商品の欄を出さなくなりますが、保存時は読み込んだ `items` をそのまま送り返します。
  `none` ↔ `list` は行き来できます

エディタ側では、商品の欄に加えて運営向けの2つの一覧（「対価が未設定の商品」
「商品が登録されていない店舗」）も出しません。**商品を掲載しないイベントでは、
どちらも指摘する意味を持たないため**です。

サーバー側（`shop-upload.php`）は変えていません。掲載するかどうかは**表示の判断**で、
受け取ったデータが仕様どおりかという**保存の判断**とは別のものです。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| 既定を `list`（従来どおり）にし、消したい人が `none` と書く | 移行は楽だが、**商品を持たないイベントで「まず消す」ところから始まる。** キットが想定する催しの幅を、既定が狭めてしまう |
| 真偽値2つ（`showItems` と `showItemList`）で表す | 「一覧は出すが取り扱いは出さない」という、**あり得ない組み合わせが書けてしまう。** 3値の列挙なら順序関係がそのまま型に出る |
| テーマからスロットを消す方法のまま、ドキュメントで案内する | いまの状態そのもの。**イベントごとにテーマを改造することになり、テーマの掛け替えで元に戻る** |
| 商品を出さないときはデータ側の `items` も消す | 掲載と保存を混ぜることになる。**一度消すと戻せない。** 期間限定で伏せる運用（開催前は出さない、など）もできなくなる |
| 出店者ごとに掲載するかどうかを選べるようにする | イベント全体の方針とは別の話で、データ仕様・エディタ・PHPの検証に波及する。**後から `shop` 側に足せる** |

## 決定の要約

| # | 決定 | なぜ重要か |
|---|---|---|
| 1 | カテゴリを設定で定義。旧形式は切り捨て。`variant` + `data-category` で見た目を分岐 | 🔴 これが無いと**他イベントでまったく使えない** |
| 6 | 出店者の入力はHTMLとして扱わない。`allowNameBreaks` 廃止。サーバーでタグ除去 | ⚠️ 配布前に方針を決めるべき安全性の問題 |
| 3 | 語彙を `shop` / `item` に改名 | 🟡 **段階3の着手前に完了させる。** 後からではテーマが壊れる |
| 2 | 開催日を設定で定義（`day1` / `day2` …）。1日開催なら販売日UIを出さない | 🟡 2日開催以外のイベントで破綻する |
| 5 | チケット運用は `price` + `pricing.mode`。小数桁に対応。併用は非対応 | 🟡 チケット制のイベントで使えない |
| 4 | 文言を辞書に外出し。日本語と英語を同梱 | 🟡 英語圏の利用者に必要 |
| 7 | 設定を `marche.config.json` に集約 | 🟡 二重管理の解消 |

### 段階2で加えた決定

| # | 決定 | なぜ重要か |
|---|---|---|
| 8 | 商品カテゴリを `marche.config.json` の `itemCategories` で定義。空なら欄を出さない | 🟡 エディタが選択肢を出せない |
| 9 | 販売日は開催日ごとのチェックボックス。全日は未指定に寄せて保存 | 🟡 3日以上の開催で破綻する |
| 10 | 保存はロスターにある店舗IDだけ受け付ける | 🟡 直接POSTで任意のフォルダを作れる穴 |
