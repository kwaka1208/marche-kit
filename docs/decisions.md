# 設計上の決定

naracraft.beer の実装を marche-kit として一般化するにあたり、決めたことの記録です。
各項目は「現状 → 何が困るか → **決定**」の順です。

決定日: 2026-08-30 / 対象: 段階1（実装着手前）

---

## 1. 出店者カテゴリは設定で定義する

### 現状（naracraft.beer）

`shops.json` のキーが `breweries` と `foodstores` の2つに固定され、
描画先のDOM IDも `#breweries-grid` / `#foodstores-grid` で決め打ちでした。

### 何が困るか

マルシェなら「野菜・加工品・雑貨・キッチンカー」、朝市なら「鮮魚・青果」のように、
区分の数も名前もイベントごとに違います。2種類固定では最初の1歩で詰まります。

### 決定

ロスターをカテゴリの配列に変え、区分そのものをデータで定義します。

```json
{
  "categories": [
    { "id": "breweries",  "label": "ブルワリー", "variant": "feature", "shops": ["choryo-brewery"] },
    { "id": "foodstores", "label": "フード",     "shops": ["yamato-tacos"] }
  ]
}
```

**旧形式（`breweries` / `foodstores` をキーにする形）は読みません。** 切り捨てます。

描画先は固定IDをやめ、テーマ側が器に属性で指定します。
カテゴリを増やすとき**テーマのHTMLに1行足すだけ**で済みます。

```html
<div class="shop-grid" data-marche-shops="breweries"></div>
```

### カテゴリごとに見た目を変える

**data属性と variant の併用**にします。コアはカードに両方を出力します。

```html
<div class="shop-card-info shop-card--feature" data-category="breweries">
```

| 手段 | 用途 | テーマの使い回し |
|---|---|---|
| `shop-card--<variant>` | **こちらを主に使う。** 見た目のバリエーション | ○ 他イベントでも当たる |
| `[data-category="..."]` | このイベント専用の微調整 | ✗ カテゴリ名が変わると当たらない |

`variant` の語彙は `standard`（既定）/ `compact` / `feature` の3つです。省略時は `standard`。

テーマは **`variant` だけを見て書くのが基本**です。カテゴリIDに直接スタイルを当てると、
そのテーマは他のイベントで使えなくなります。逃げ道として残しますが、常用しません。

## 2. 開催日は設定で定義する

### 現状

商品の販売日が `both` / `dayA` / `dayB` の3値で、**2日間開催が前提**でした。
表示ラベル（「3日(土)のみ」など）は描画JSとエディタに直書きでした。

### 何が困るか

1日開催、3日開催のイベントで破綻します。日付の表記も毎年書き換えが必要でした。

### 決定

開催日をサイト設定に配列で持ちます。IDは **`day1` / `day2` / … の連番**とし、
後ろの数字だけが変わる形にします。

```json
"days": [
  { "id": "day1", "date": "2026-10-03", "label": "10月3日(土)", "shortLabel": "3日(土)" },
  { "id": "day2", "date": "2026-10-04", "label": "10月4日(日)", "shortLabel": "4日(日)" }
]
```

商品側は**日のIDの配列**を持ちます。省略時は全日です。

```json
"saleDays": ["day1"]
```

ラベルは設定から取るので、年度更新はサイト設定の1箇所で完結します。
旧形式（`both` / `dayA` / `dayB`）は読みません。

**1日開催のとき（`days` が1件）は、販売日のUIを出しません。**
サイト表示からもエディタの選択欄からも消えます。「初日のみ」の選択肢に意味がないためです。

## 3. 語彙を改名する

### 現状

コード全体で `menu`（商品）、`brewery` / `foodstore`（出店者）という語が使われ、
CSSクラス名にも `menu-card-top` / `menu-image` として現れていました。

### 何が困るか

雑貨のマルシェで `menu` は不自然です。第三者がコードを読むとき、
`menu` がナビゲーションメニューなのか商品なのかも紛らわしくなります。

### 決定

| 旧 | 新 |
|---|---|
| `brewery` / `foodstore` / `vendor` | **`shop`** |
| `menu` / `menus` | **`item`** / `items` |

クラス名も追随します（`menu-card-top` → `item-card-top` など）。

**この改名は段階3の着手前に完了させます。** クラス名はテーマ契約の一部であり、
後から変えると既存のテーマがすべて壊れるためです。

## 4. 表示文言を辞書に外出しし、英語辞書を同梱する

### 現状

「完売しました」「読み込み中…」「過去のお知らせを見る」などがコードに直書きでした。

### 決定

文言を辞書JSONにまとめ、サイト設定の `locale` で選びます。
**日本語と英語の辞書を同梱します。**

```
core/i18n/ja.json
core/i18n/en.json
```

本格的な多言語対応（i18nライブラリ、言語切り替えUI、URLの言語別分岐）は入れません。
**辞書1枚で足ります。** サイトごとに一部の文言だけ差し替えられるようにします。

## 5. チケット運用は price の読み替えで対応する

### 現状

`price` は数値で、表示時に円として整形されていました。

### 何が困るか

イベントによっては、会場共通のチケットを先に買い、商品はチケット◯枚と引き換える
**チケット運用**をとります。この場合に見せたいのは「600円」ではなく「2枚」です。

本家サイトも第6回まではチケット運用で、`tickets` という別フィールドを持っていました。

### 実データから分かったこと

本家の全131商品を調べたところ、`tickets` と `price` の**共存は1件もありませんでした。**

| 状態 | 件数 |
|---|---|
| `tickets` のみ（チケット運用時代） | 75 |
| `price` のみ（金額制移行後） | 44 |
| 両方を持つ | **0** |

運用は排他で、1つのイベントの中で金額とチケットが混在することはありません。

### 決定

`tickets` フィールドは復活させません。`price` を「**対価を表す数値**」と定義し直し、
**表示の単位だけを設定で切り替えます。**

```json
"pricing": {
  "mode": "currency",
  "currency": { "unit": "円", "position": "suffix", "grouping": true, "decimals": 0 },
  "ticket":   { "unit": "枚", "faceValue": 300, "showFaceValue": true },
  "note": "税込"
}
```

**通貨の小数桁に対応します**（`decimals`）。円は `0`、ドルやユーロは `2` を指定します。
チケットモードでは枚数なので、`decimals` は使わず**常に整数**として検証します。

**チケットと現金の併用（「チケット2枚 または 600円」）は対応しません。**
実運用に前例がなく、データ構造が複雑になるためです。

既存の規約はそのまま活きます。`price` が0以下なら未設定とみなして一覧に出さないルールは、
「0枚」が無意味であることと自然に整合します。

### 但し書きも設定から与える

現行実装は商品詳細に「税込」を直書きしていました（`script.js:316`）。
チケット運用では税の概念がないため、これも設定の `pricing.note` から与えます。
**空なら要素ごと出力しません。**

## 6. 出店者が入力する文字列はHTMLとして扱わない

### 現状

出店者が編集できる項目のうち、HTMLとして描画される箇所とテキストとして描画される箇所が
混在していました。

| 項目 | 描画方法 |
|---|---|
| 店名（`name`） | 常にHTMLとして挿入 |
| 商品名（`menus[].name`） | 既定は `<br>` を空白に置換してテキスト描画。`allowNameBreaks: true` のときだけHTML |
| 紹介文（`comment`） | `\n` を `<br>` に変換。テキスト扱い |
| お知らせ（`body`） | HTML文字列 |

### 何が困るか

店名と `allowNameBreaks: true` の2経路では、出店者エディタから任意のHTMLを保存できます。
**理屈の上ではスクリプトを仕込めます。**
現行サイトでは出店者が身元の知れた相手であり、実害がないため許容されていました。

しかしOSSとして配布すると、利用者の運用体制はさまざまです。
「出店者を信頼する前提」を暗黙にしたまま配るのは不親切です。

### 決定

**店名と商品名の `<br>` 埋め込みを廃止し、`\n` を改行として扱う方式に統一します。**
`comment` がすでにこの方式で、実績があります。

**`allowNameBreaks` は廃止します。** 統一により不要になります。

**サーバー側でHTMLタグを除去する検証を入れます。**
クライアントを信用せず、保存時にタグを落とします。

**READMEに「出店者を信頼できる範囲で使う仕組み」であることを明記します。**
承認フローを持たない設計である以上、この前提は隠さず書きます。

お知らせの `body` はHTML文字列のままにします。運営しか書けないためです。

## 7. 設定をフレームワーク非依存のJSONに集約する

### 現状

サイト共通情報・開催概要・お知らせ設定が、Astroのソース内のTypeScriptファイルにありました。

### 何が困るか

静的サイトジェネレーターを変えると設定ごと移植が必要になります。
またPHP側からは読めないため、設定が二重管理になっていました。

### 決定

イベント設定を `marche.config.json` に集約し、**サイト生成側もPHP側も同じファイルを読みます。**
年度更新がこの1ファイルで完結する状態を目指します。

```json
{
  "site":    { "name": "...", "url": "...", "description": "..." },
  "event":   { "year": 2026, "venue": "...", "hours": "..." },
  "days":    [ { "id": "day1", "date": "2026-10-03", "label": "10月3日(土)", "shortLabel": "3日(土)" } ],
  "pricing": { "mode": "currency", "currency": { "unit": "円", "position": "suffix", "grouping": true, "decimals": 0 } },
  "locale":  "ja",
  "announcements": { "source": "data/news.json", "visibleCount": 3 }
}
```

TypeScriptの型による恩恵は失われますが、二重管理の解消を優先します。
型が必要なら、JSONから型定義を生成する方法をあとで検討します。
